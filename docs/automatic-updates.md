# Automatic updates: desktop and Cylinder

Desktop, Cylinder Server, and Cylinder Client check before opening the main workspace when due. A saved `lastAttemptAt` in each edition's `update-preferences.json` limits automatic checks to once every 72 hours, including across app restarts. First launch with no recorded attempt checks immediately. Offline or failed attempts count toward the interval. Manual Firebase Check and re-enabling Auto-Check respect the same limit.

While the app remains open, a local timer checks eligibility once a minute; it makes no network requests until the 72 hours have elapsed. Startup waits are bounded, so an unavailable update service does not prevent opening the workspace. A check already in progress cannot be duplicated.

Automatic checking defaults on. An existing explicit Auto-Check off preference remains respected. Desktop, Cylinder Server, and Cylinder Client retain separate data directories and update feeds. Downloads happen through the updater's automatic download mechanism and install on app exit; this setting does not silently force a restart.

Firebase Hosting is the canonical update and installer distribution source. Desktop uses `https://overhead-office.web.app/updates/latest.yml`; Cylinder Server uses `https://overhead-office.web.app/updates/cylinder/latest.yml`; Cylinder Client uses `https://overhead-office.web.app/updates/cylinder-client/latest.yml`. If Firebase cannot serve a valid feed, the client may fall back to a matching stable release in the public `ghostventure/GhostVenture-Projects` GitHub repository. The GitHub fallback requires a matching `latest.yml` and product-specific Windows installer.

The Updates panel also has a dedicated **Check GitHub** action. It directly checks the public stable releases, bypassing the normal 72-hour eligibility window for that user-requested check, then records the attempt so automatic checks wait for the next window. A newer version in the same major version is classified as incremental and downloads in the background for installation when the app closes. A changed major version is classified separately; the same NSIS package supports silent in-app installation through `electron-updater` and the regular installer wizard through the product-specific GitHub installer download. The GitHub download is opened only from a validated `https://github.com/` asset URL. Releases still need a product-matching `latest.yml`, installer, and blockmap for differential transfer; without a compatible feed, the regular installer remains the full-package route.

The GitHub check is an update discovery path; it does not publish a release. A release must be built and uploaded with assets matching the app edition and version. Test the public release metadata and asset selection, then verify the packaged app's downloaded-update and major-version installer paths on an installed build. A passing source test does not establish that the live GitHub release or Firebase feed contains the current app.

Validation: `node --test scripts/update-schedule.test.cjs scripts/github-release.test.cjs` checks persisted throttling, concurrency, failed requests, expiry, preservation of a downloaded update, and GitHub release asset selection. Changed packages must be rebuilt and installed before existing installations gain this behavior.

The 0.3.13 installers in `release-updates-desktop-0.3.13` and `release-updates-cylinder-0.3.13` predate this release selection and do not include it. This source change still needs a new packaged release before installed clients can use it; it has not been published to Firebase or GitHub.

## Central release workspace

`npm run release:prepare` builds both signed Windows products into `release/current/desktop` and `release/current/cylinder`, with separate versioned installers, ZIPs, checksum files, and updater manifests. Both products use the desktop version from `package.json`. Set `CSC_LINK`, `CSC_KEY_PASSWORD`, and `OVERHEAD_EXPECTED_SIGNER` first. `npm run release:plan` prints the shared version and artifact names without building. After inspecting both outputs, `npm run release:deploy` checks both installer signatures and publishes the two feeds and downloads in one Firebase Hosting release. Firebase Tools is discovered from the local or npm cache install; set `OVERHEAD_FIREBASE_TOOLS` only to pin a specific installation. Finish with `npm run release:verify` to compare public manifests and installer hashes to the staged release. Desktop and Cylinder retain separate app identities, local data roots, and update paths.
